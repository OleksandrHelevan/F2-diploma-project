# DVO-L4-3C8B52
# Лабораторна робота №3 — Технології DevOps
## Розгортання власного застосунку в Kubernetes

### Мета

Описати власний застосунок (той самий, що використовувався в попередніх лабораторних) набором маніфестів Kubernetes, розгорнути його в локальному кластері minikube та продемонструвати керування життєвим циклом застосунку засобами kubectl.

### Завдання

1. Підготувати образ застосунку:
   - використати образ власного проєкту;
   - опублікувати образ у registry або завантажити його у minikube;
   - використовувати конкретний тег версії, не `latest`;
   - підготувати щонайменше дві версії образу (наприклад 1.0.0 і 1.1.0).
2. Розгорнути локальний кластер:
   - встановити minikube та kubectl;
   - запустити кластер з драйвером Docker;
   - перевірити вузол і системні поди у `kube-system`;
   - увімкнути доповнення metrics-server та ingress.
3. Створити окремий namespace для проєкту за назвою проєкту або прізвищем; подальші об'єкти створювати лише в ньому.
4. Описати маніфести у `k8s/`, по одному файлу на об'єкт:
   - Deployment не менше ніж з двома репліками, узгодженими labels/selector, CPU та memory requests/limits, liveness/readiness probes;
   - Service для доступу всередині кластера та з хоста;
   - ConfigMap щонайменше з двома параметрами конфігурації;
   - Secret щонайменше з одним чутливим параметром;
   - Ingress або NodePort;
   - PersistentVolumeClaim для компонентів зі станом.
5. Розгорнути застосунок:
   - застосувати маніфести однією командою з каталогу;
   - показати Pods, Deployment, ReplicaSet і Service;
   - відкрити застосунок у браузері;
   - підтвердити надходження параметрів ConfigMap і Secret до контейнера.
6. Продемонструвати керування життєвим циклом:
   - видалити Pod та показати його самовідновлення;
   - масштабувати репліки й показати endpoint/розподіл трафіку;
   - оновити образ до другої версії та показати rolling update;
   - показати rollout history та відкотити до попередньої ревізії;
   - показати доступність застосунку під час оновлення.
7. Виконати діагностику:
   - вказати неіснуючий тег і показати `ImagePullBackOff`;
   - знайти причину через describe та Events;
   - показати container logs та інтерактивний exec;
   - виправити тег і повернути застосунок у робочий стан.
8. Оформити результати:
   - додати `k8s/` до репозиторію;
   - описати порядок розгортання та ConfigMap/Secret у README;
   - підготувати звіт зі скриншотами/виводом команд для пунктів 5–7.

### Вимоги до здачі

- Маніфести написані вручну або на основі прикладів лекції, а не залишені необробленим виводом `kubectl create -o yaml`.
- У Secret немає реальних паролів від робочих систем.
- Застосунок має розгортатися з нуля однією командою `kubectl apply -f k8s/`.

### Виконання та обмеження середовища

Створено маніфести у `k8s/` для сервісів Bricklayers та інфраструктурних компонентів, окремий namespace, ConfigMap, демонстраційний Secret, PVC для PostgreSQL/MongoDB, NodePort для web-app, liveness/readiness TCP probes і кафедральне маркування всіх об'єктів. Додано скрипт для локальної збірки/завантаження образів із тегом, README з командами життєвого циклу та DOCX-звіт із місцями для доказових скриншотів.

Docker CLI встановлений, але Docker Engine недоступний; `minikube status` не проходить, оскільки minikube container не запущений. Тому створити образи, застосувати YAML до кластера, показати браузер і зробити справжні скриншоти з цього робочого середовища неможливо. DOCX чітко позначає кожне місце, потрібні команди й очікуваний тип доказу; фактичні результати кластера не сфабриковані.

У репозиторії не було попередніх k8s YAML лабораторної №3 або registry-образів. Для власних образів задано локальні імена `bricklayers/*` з тегами `1.0.0`; скрипт приймає версійний тег, щоб зібрати також `1.1.0` після зміни коду. Паролі у маніфесті Secret — локальні заглушки, які слід замінити перед використанням; не додавати робочі облікові дані до Git.
