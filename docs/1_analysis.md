## 1.2. Огляд сучасних підходів до вирішення відповідних завдань

Аналіз еталонних архітектурних напрямів дозволив виокремити чотири групи підходів, релевантних темі дослідження.

**Cloud-Native мікросервісна архітектура.** Підхід передбачає декомпозицію бізнес-логіки на незалежно розгортувані сервіси, контейнеризацію (Docker) та оркестрацію (Kubernetes), а також проєктування міжсервісної комунікації: синхронної (REST) та асинхронної (брокер повідомлень). Перевагою є незалежне масштабування компонентів із різним профілем навантаження (потік геокоординат і облік заявок мають різну інтенсивність). Недоліком є зростання операційної складності: розподілене трасування, версіонування контрактів, відсутність глобальних ACID-транзакцій.

**Event-driven взаємодія та розподілена консистентність.** Відсутність розподілених транзакцій компенсується патернами Saga (послідовність локальних транзакцій з компенсуючими діями; варіанти — оркестрація та хореографія), Transactional Outbox (атомарний запис зміни стану та події в одній локальній транзакції СУБД) і CQRS (розділення моделей запису та читання). Доставка повідомлень брокером типу Apache Kafka забезпечує семантику at-least-once, тому споживачі мають бути ідемпотентними, а необроблені повідомлення — спрямовуватися до черги недоставлених повідомлень (Dead Letter Queue, DLQ). Альтернативою є RabbitMQ, орієнтований на маршрутизацію та черги, тоді як Kafka надає журнал подій із можливістю повторного відтворення; вибір підлягає фіксації в ADR.

**Відмовостійкість та інтеграція інтелектуальних компонентів.** Зовнішній LLM API розглядається як ненадійна залежність із непередбачуваною затримкою. Стандартною практикою є застосування Circuit Breaker, Retry з експоненційною затримкою, Bulkhead (ізоляція пулу потоків) і Timeout, реалізованих бібліотекою Resilience4j. Інтелектуальний компонент виділяється в окремий сервіс із чітким контрактом (вхідні/вихідні дані, обробка помилок) та консультативним статусом: остаточне рішення залишається за людиною.

**Геопросторова верифікація та безпека.** Верифікація присутності реалізується через геозонування: перевірка належності координат пристрою полігону об'єкта просторовими функціями PostGIS (ST_Contains, ST_DWithin) із кешуванням активних сесій у Redis. Критичним обмеженням є точність GPS та можливість підміни координат, тому правила детекції аномалій генерують сповіщення для перевірки людиною, а не автоматичне рішення. Автентифікація базується на OAuth 2.0 / OpenID Connect із підписаними JWT та RBAC; обробка геоданих підпорядкована принципам мінімізації та обмеження зберігання (GDPR, Закон України «Про захист персональних даних»).

**Інженерія якості та спостережуваність.** Сучасною практикою є автоматизація збирання й тестування (CI/CD, GitHub Actions), піраміда тестів (модульні, інтеграційні, контрактні, навантажувальні), метрики й алертинг (Prometheus, Grafana), централізоване логування та розподілене трасування (OpenTelemetry).

## 1.3 Аналіз та порівняння існуючих рішень на ринку готових програмних продуктів

Для порівняння обрано три платформи управління будівництвом: Procore, Fieldwire та Autodesk Construction Cloud (ACC). Для кожного твердження зазначено рівень достовірності: **В** – підтверджено публічною документацією; **С** – підтверджено непрямими джерелами (вакансії вендора, вторинні огляди); **Н** – не підтверджено, подано як припущення.

### 1.3.1 Procore

**Архітектурний патерн.** Multi-tenant SaaS. За даними вакансій вендора, ядро реалізовано як монолітний застосунок на Ruby on Rails із планованою еволюцією в модульну систему з чіткими межами доменів (С). Окремі сервіси реалізуються також на Node.js і Java; розгортання здійснюється на AWS та Kubernetes (С). Монолітна структура спрощує транзакційну цілісність, проте зумовлює зв'язність доменних модулів і обмежує їх незалежне масштабування.

**Протоколи взаємодії.** REST API (JSON), OAuth 2.0 з потоками Authorization Code і Client Credentials, Webhooks (В). Документація зазначає можливість надходження дублікатів подій до споживача; доставка супроводжується механізмом retry/backoff.

**Стек даних.** PostgreSQL (С, за вакансіями). Використання кешу в пам'яті та об'єктного сховища в публічних джерелах не підтверджено. Консистентність у межах ядра забезпечується транзакціями реляційної СУБД (виведено з використання PostgreSQL); для зовнішніх інтеграцій діє eventual consistency.

**Technical Bottlenecks.** Зв'язність доменних модулів у моноліті ускладнює незалежне масштабування. Ідемпотентність обробки Webhooks покладено на споживача. Ліміт API становить 3600 запитів на годину, що обмежує пакетну синхронізацію. Нативну геопросторову верифікацію присутності за публічною документацією API не виявлено.

### 1.3.2 Fieldwire

**Архітектурний патерн.** Multi-tenant SaaS із мобільними клієнтами. За вакансіями, серверна частина використовує Ruby on Rails і AWS, також згадуються Docker і Rust (С). Монолітність серверної частини публічно не підтверджено, структура не розкривається. Offline-first модель клієнта з локальним сховищем не перевірялась (Н).

**Протоколи взаємодії.** REST API (JSON) та Webhooks (В). Автентифікація двоетапна: довгоживучий API-токен обмінюється на короткоживучий JWT; Webhooks обслуговуються окремим сервісом (С).

**Стек даних.** PostgreSQL (С, згадується в одній вакансії); об'єктне сховище для файлів (В: завантаження файлів виконується через AWS-токен у S3-сховище). Консистентність між клієнтом і сервером, імовірно, eventual (Н).

**Technical Bottlenecks.** Ліміт становить 10 запитів на секунду на токен; при перевищенні повертається код 429. Доступ до API надається лише для тарифу Enterprise або як додаткова послуга до тарифів Pro і Business. Offline-синхронізація (за наявності) вимагає стратегії розв'язання конфліктів одночасних змін. Геопросторову верифікацію присутності за публічною документацією API не виявлено.

### 1.3.3 Autodesk Construction Cloud (ACC)

**Архітектурний патерн.** Хмарна платформа, доступна через Autodesk Platform Services (APS). Внутрішня архітектура публічно не розкривається (Н). Обробку моделей через асинхронні пайплайни трансляції подано як припущення, що не перевірялось (Н).

**Протоколи взаємодії.** REST API, OAuth 2.0 у режимах 2-legged і 3-legged, Webhooks API (В). GraphQL доступний лише в межах AEC Data Model API, що надає GraphQL-інтерфейс до гранулярних даних моделей, переважно на читання. Решта API реалізована як REST.

**Стек даних.** Внутрішній стек не розкривається (Н). Через APS доступний уніфікований шар Data Management для BIM 360, ACC та Docs.

**Technical Bottlenecks.** Ліміти різняться за ендпоїнтами та документовані неоднорідно. Доступ для client ID має надати кожен адміністратор акаунта, тому розгортання інтеграції виконується послідовно. Для токен-ендпоїнта відомий ліміт 500 викликів на хвилину. Спеціалізований сценарій геоверифікації присутності та контролю робочого часу за документацією API не виявлено.

### 1.3.5 Аналітичний висновок до підрозділу 1.3

Аналіз Procore, Fieldwire та ACC виявив низку архітектурних обмежень, характерних для універсальних платформ управління будівництвом. За даними вакансій вендора, ядро Procore має монолітну Rails-структуру, що модуляризується; така структура спрощує транзакційну цілісність, проте зумовлює зв'язність доменних модулів і ускладнює їх незалежне масштабування та релізний цикл. Для Fieldwire монолітність не підтверджено, структура серверної частини не розкривається; offline-синхронізація клієнтів потребує стратегії розв'язання конфліктів, що за простих політик (last-write-wins) допускає втрату проміжних змін. Внутрішня архітектура ACC не документована. Інтеграція із зовнішніми системами в усіх аналогах ґрунтується на REST API та Webhooks. Вона підлягає обмеженню квотами: 3600 запитів/год для Procore, 10 запитів/с на токен для Fieldwire, різні ліміти за ендпоїнтами для ACC. Документація Procore допускає дублікати подій Webhooks, тому ідемпотентність обробки покладено на споживача. За публічною документацією API жоден з аналогів не реалізує геопросторову верифікацію присутності з перевіркою координат відносно геозони та інваріантом єдиної активної сесії.

Обрана архітектура Bricklayers усуває ці обмеження за рахунок декомпозиції на незалежно розгортувані мікросервіси з подієвою взаємодією через Apache Kafka. Застосування Transactional Outbox, ідемпотентних споживачів і Dead Letter Queue забезпечує коректну обробку подій за семантики повторної доставки та запобігає подвійному нарахуванню робочого часу. Узгодженість розподілених бізнес-транзакцій (життєвий цикл заявки на матеріали) забезпечується оркестрованою Saga з компенсуючими транзакціями, а розділення навантажень запису й читання за патерном CQRS унеможливлює вплив потоку геокоординат на транзакційну БД. Стійкість до збоїв зовнішнього LLM API забезпечується Resilience4j (Circuit Breaker, Retry, Bulkhead), геопросторова верифікація реалізується засобами PostGIS, наскрізна спостережуваність – засобами OpenTelemetry, Prometheus та Grafana.

Водночас обраний підхід має компроміс (trade-off): мікросервісна архітектура з Kafka та Kubernetes підвищує операційну складність, вартість експлуатації інфраструктури й вимоги до тестування порівняно з монолітом, а eventual consistency ускладнює аналіз стану системи. У межах кваліфікаційної роботи цей компроміс визнано виправданим, оскільки предметна область характеризується піковим навантаженням (ранкова реєстрація присутності), безперервним потоком геоданих і вимогою до перевірюваності облікових процесів. Обґрунтування вибору Kafka порівняно з RabbitMQ та оркестрації порівняно з хореографією Saga наведено в Розділі 2 (Проєктування).

## 1.4. Аналіз обраної предметної області в межах дослідження (модель As-Is)

### 1.4.1. Загальна характеристика домену

Предметною областю є цифрове управління будівельним виробництвом (Construction Management Software), що охоплює планування робіт, облік робочого часу та присутності персоналу, логістику матеріальних ресурсів, контроль якості та звітність перед замовником і фінансуючими сторонами. Для України домен набуває специфічних рис у зв'язку з повоєнним відновленням: зростає кількість територіально розподілених об'єктів, підвищуються вимоги до прозорості використання публічних і донорських коштів, обмежена доступність кваліфікованих кадрів збільшує вартість помилок обліку.

Сучасні тенденції домену станом на 2026 рік: перехід від локальних рішень до хмарних multi-tenant платформ; мобільні та Progressive Web Application клієнти з доступом з об'єкта; використання геопросторових даних для підтвердження присутності та контролю периметра; інтеграція великих мовних моделей як консультативного компонента; подієво-орієнтована інтеграція підсистем замість синхронного обміну; зростання вимог до спостережуваності та автоматизованого забезпечення якості.

### 1.4.3. Бізнес-процеси та Workflows (As-Is)

**Процес 1. Облік присутності та робочого часу.** Прораб фіксує присутність бригади в паперовому табелі або в чаті месенджера. Дані пересилаються відповідальній особі та вручну переносяться в електронну таблицю для нарахування. Потік даних: пристрій → месенджер → ручний ввід → облікова таблиця. Встановлено відсутність автоматичної верифікації координат, допустимість ретроспективного внесення записів та відсутність обмеження «одна активна сесія на працівника», що зумовлює подвійне нарахування та неможливість аудиту.

**Процес 2. Заявка на матеріали та постачання.** Заявка узгоджується телефоном або в месенджері: прораб → замовник → постачальник. Стан заявки не зберігається у спільному сховищі, ціна визначається на момент поставки, а не на момент заявки; повторна відправка повідомлення створює дублікат. З точки зору розподілених систем це розподілена бізнес-транзакція без координатора та без компенсуючих дій: відмова або зміна ціни на одному з етапів не призводить до узгодженого відкату.

**Процес 3. Фіксація прогресу та дефектів.** Фотографії та описи надсилаються в загальні чати без структурованих метаданих. Попередня оцінка дефекту очікує на залучення експерта, історія рекомендацій відсутня, замовник не має підтвердженого факту ознайомлення зі звітом.

**Таблиця 1.3. Локалізація вузьких місць (bottlenecks)**

| Процес | Вузьке місце | Технічна природа | Наслідок |
| --- | --- | --- | --- |
| Облік присутності | Ручне перенесення даних; відсутня геоверифікація | Відсутність валідації на вході та інваріантів | Затримка звітності до кількох діб; подвійні й недостовірні записи |

| Прогрес і дефекти | Неструктуровані канали, відсутність історії | Відсутня модель даних і аудит | Втрата контексту; затримка кваліфікованої оцінки |
| Інтеграція підсистем | Синхронний ручний обмін | Відсутність подієвої шини | Висока латентність узгодження стану |

### 1.4.4. Регуляторні та індустріальні обмеження

Установлено такі обмеження, що діють у предметній області:

- **Захист персональних даних.** Геолокація працівника є персональною інформацією. Застосовується Закон України «Про захист персональних даних»; як індустріальний орієнтир враховано принципи GDPR (законність, мінімізація даних, обмеження зберігання, оцінка впливу на захист даних за ст. 35 для систематичного моніторингу).
- **Безпека застосунків.** OWASP Top 10 та OWASP ASVS (рівень 2) як еталон вимог до автентифікації, керування сесіями та контролю доступу.
- **Протоколи автентифікації.** OAuth 2.0 (RFC 6749), OpenID Connect Core 1.0, JSON Web Token (RFC 7519).
- **Геопросторові стандарти.** WGS 84, GeoJSON (RFC 7946), OGC Simple Features; Web Geolocation API вимагає захищеного контексту (HTTPS) та явної згоди користувача.
- **Веб-стандарти клієнта.** W3C Service Workers, Web Push (RFC 8030, VAPID — RFC 8292) для PWA.
- **Якість ПЗ та документація.** ISO/IEC 25010 (модель якості), ДСТУ 3008:2015 (оформлення документів), ДБН А.3.1-5:2016 «Організація будівельного виробництва» як нормативний контекст процесів.
- **Зовнішні AI-сервіси.** Передача даних стороннім провайдерам LLM потребує виключення персональних і геопросторових даних із запитів.

### 1.4.5. Висновок підрозділу

Встановлено, що вузькі місця процесів As-Is мають інженерну природу: відсутність єдиного джерела істини, валідації на вході, ідемпотентності, подієвої інтеграції та аудиту. Ручні канали передачі даних зумовлюють затримки узгодження стану, а відсутність формалізованих інваріантів — недостовірність записів. Це обґрунтовує необхідність автоматизації, що розглядається в підрозділі 1.5.

## 1.5. Постановка задачі та формування вимог (модель To-Be, Core Features, NFRs)

### 1.5.1. Концептуальна модель To-Be

Цільовий стан передбачає заміну розрізнених каналів єдиною розподіленою платформою, де кожна зміна стану об'єкта фіксується як подія предметної області. Облік присутності переноситься у сервіс обліку робочого часу: прораб генерує QR-сесію з обмеженим терміном дії, пристрій будівельника передає координати, а PostGIS перевіряє належність точки полігону геозони; інваріант «одна активна сесія на працівника» гарантується на рівні сховища, що усуває подвійне нарахування. Активні сесії кешуються в Redis, що скорочує латентність перевірок. Розділення моделей запису й читання (CQRS) ізолює потік геокоординат від транзакційної бази даних; позиції активних учасників зберігаються в Redis (GEO).

Життєвий цикл заявки на матеріали реалізується як оркестрована Saga з компенсуючими транзакціями: формування заявки → погодження замовником → замовлення постачальнику → фіксація снапшота ціни → автоматичне повернення при відхиленні ціни понад N % → приймання з реєстрацією розбіжностей. Зміни стану публікуються через Transactional Outbox в Apache Kafka, споживачі є ідемпотентними, необроблені повідомлення спрямовуються до DLQ. Звернення до LLM API захищені Circuit Breaker, Retry та Bulkhead (Resilience4j); відмова зовнішнього сервісу не блокує основні процеси. Аномалії присутності формують сповіщення для верифікації людиною без автоматичного рішення алгоритму. Контейнеризація (Docker), оркестрація (Kubernetes), CI/CD (GitHub Actions) та спостережуваність (Prometheus, Grafana, OpenTelemetry) формують операційний контур.

### 1.5.2. Функціональні вимоги (Core Features)

**Модуль автентифікації та доступу (auth-service)**

- Автентифікувати користувачів за OAuth 2.0 / OpenID Connect із видачею підписаних JWT та розмежовувати доступ за п'ятьма ролями (RBAC) з перевіркою належності ресурсу (ownership) на рівні API та веденням audit trail.
- Блокувати акаунти з автоматичним завершенням усіх активних сесій заблокованого користувача.

**Модуль обліку робочого часу та геолокації (attendance-service)**

- Генерувати часово обмежені QR-сесії та верифікувати check-in/check-out відносно геозони об'єкта засобами PostGIS із інваріантом єдиної активної сесії на користувача й автоматичним обчисленням відпрацьованого часу.
- Приймати потік геокоординат активних сесій, зберігати їх у Redis, відображати позиції на карті (Leaflet, OpenStreetMap) та детектувати аномалії (вихід за геозону, відсутність зміни координат понад поріг, конфігурований на рівні об'єкта) із формуванням сповіщення для верифікації людиною.

**Модуль заявок та завдань (order-service, task-service)**

- Керувати життєвим циклом заявки на матеріали за схемою Saga з компенсуючими транзакціями, фіксацією снапшота ціни, автоматичним поверненням при відхиленні понад N % та реєстрацією розбіжності факт/заявка при прийманні.
- Створювати завдання, призначати бригаді чи виконавцю, відстежувати статус із обов'язковим підтвердженням закриття прорабом.

**Модуль AI-аналізу та звітності (ai-service, report-service, notification-service)**

- Формувати консультативну оцінку текстового опису дефекту через Gemini API (Circuit Breaker, Retry, Bulkhead), зберігати історію рекомендацій та позначати їх як консультативні.
- Публікувати структуровані записи прогресу (зображення, опис, часова позначка) у хронологічній стрічці з реєстрацією факту перегляду замовником; розсилати push-сповіщення за подіями через Apache Kafka (Transactional Outbox, ідемпотентні споживачі, DLQ).

### 1.5.4. Постановка задачі

Таким чином, метою кваліфікаційної роботи є проєктування та розробка розподіленої подієво-орієнтованої мікросервісної платформи для вирішення задачі верифікованого обліку робочого часу, матеріальних ресурсів та ходу робіт на будівельному об'єкті. Передбачено реалізацію Saga-координації життєвого циклу заявок, геопросторової верифікації присутності засобами PostGIS, ідемпотентної обробки подій (Transactional Outbox, Apache Kafka) та захищеної інтеграції з LLM API (Resilience4j). Встановлено цільові показники: p95 латентності читання ≤ 200 мс при 500 RPS, доступність 99,5 %, автентифікація OAuth 2.0 / OIDC із підписаними JWT, контейнеризація та розгортання в Kubernetes.

## Висновки до розділу 1

Аналіз сучасних підходів та існуючих рішень (Procore, Fieldwire, Autodesk Construction Cloud) показав, що універсальні хмарні платформи орієнтовані на документообіг і загальне управління проєктом. Для них встановлено жорсткі ліміти зовнішніх API, перенесення відповідальності за ідемпотентність обробки подій на інтегратора та відсутність нативного механізму геопросторової верифікації присутності й контролю робочого часу за публічною документацією. Для частини платформ архітектура належить до модульного моноліту зі зв'язністю доменних модулів, що обмежує незалежне масштабування. Аналіз процесів As-Is виявив, що ручні канали обміну даними зумовлюють відсутність єдиного джерела істини, подвійний облік, дублікати заявок та затримку узгодження стану.

Обраний шлях обґрунтовується відповідністю архітектурних рішень виявленим вузьким місцям. Event-driven мікросервісна архітектура з Apache Kafka та Transactional Outbox усуває синхронну залежність підсистем; Saga з компенсуючими транзакціями забезпечує узгодженість життєвого циклу заявки; CQRS ізолює потік геокоординат від транзакційної бази даних; PostGIS і Redis реалізують геоверифікацію присутності з інваріантом єдиної активної сесії; Resilience4j ізолює відмови зовнішнього LLM API. Стек Java, Spring Boot, PostgreSQL, React (PWA) і Kubernetes забезпечує досяжність цільових показників (p95 ≤ 200 мс при 500 RPS, доступність 99,5 %, OAuth 2.0 / OIDC із підписаними JWT). Компромісом є зростання операційної складності, що компенсується автоматизацією CI/CD та спостережуваністю.

Аналітичне й практичне вирішення виявлених проблем, а також технічна реалізація сформульованих функціональних та нефункціональних вимог стануть предметом поглибленого розгляду в Розділі 2 (Проєктування: архітектура C4, модель даних, специфікації API, алгоритми критичних вузлів) та Розділі 3 (Реалізація: розробка сервісів, розгортання, тестування та аудит якості й безпеки).
