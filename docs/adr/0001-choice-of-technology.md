## Context (Контекст)

Сім доменних сервісів Bricklayers обмінюються станом виключно через доменні події ([C4 Level 2](../2_design.md#diagram-level2)): синхронні виклики між сервісами заборонені, щоб відмова одного сервісу не блокувала check-in, заявки та сповіщення. Кожен сервіс публікує події через Transactional Outbox, споживачі будують локальні проєкції (геозони, призначення, блокування користувачів) та надсилають сповіщення.

Брокер повинен задовольнити такі обмеження SRS:

| Рушій рішення | Кількісна вимога | Джерело |
| --- | --- | --- |
| D1. Пропускна здатність | Потік подій присутності ≈ 84 повідомлення/с у штатному режимі, пік check-in 300 подій за 5 хв, сумарно з іншими доменами ≤ 200 повідомлень/с | [SRS-NFR-PERF-04](../srs.md#srs-nfr-perf-04), [SRS-NFR-PERF-03](../srs.md#srs-nfr-perf-03) |
| D2. Латентність | p95 «commit → передача в Web Push» ≤ 2 с | [SRS-NFR-PERF-06](../srs.md#srs-nfr-perf-06) |
| D3. Порядок | Строгий порядок подій у межах однієї заявки (Saga) та однієї робочої сесії | [SRS-FUN-18](../srs.md#srs-fun-18), [SRS-FUN-09](../srs.md#srs-fun-09) |
| D4. Довговічність | Підтвердження запису двома репліками, відсутність втрат при відмові одного вузла | [SRS-NFR-REL-03](../srs.md#srs-nfr-rel-03) |
| D5. Повторне читання | Перебудова проєкції нового або відновленого сервісу з історії подій за 7 діб без звернення до сервісу-власника | [SRS-NFR-REL-05](../srs.md#srs-nfr-rel-05) |
| D6. Обробка збоїв | 5 повторів з експоненційною затримкою, далі DLQ | [SRS-NFR-REL-04](../srs.md#srs-nfr-rel-04) |
| D7. Ресурсний бюджет | Увесь кластер dev ≤ 8 vCPU / 16 GiB RAM (minikube) | [SRS-NFR-INFRA-02](../srs.md#srs-nfr-infra-02), [SRS-CON-01](../srs.md#srs-con-01) |

Рушії D1 і D2 не є визначальними: усі розглянуті альтернативи забезпечують ≥ 10⁴ повідомлень/с і мілісекундну латентність на одному вузлі. Вибір визначають D3, D5, D6 і D7.

## Alternatives (Розглянуті альтернативи)

### A. Apache Kafka 3.8 (KRaft, 3 брокери)

Розподілений журнал подій з розбиттям топіків на партиції.

- **Переваги:** порядок гарантується в межах партиції за ключем повідомлення (`requestId`, `sessionId`) — D3; повідомлення зберігаються за політикою retention незалежно від факту споживання, consumer group може повторно прочитати топік із довільного offset — D5; log compaction для топіків стану (`site.geofences`) дозволяє зберігати останню версію геозони без обмеження за часом; ідемпотентний producer і `acks=all` з `min.insync.replicas=2` — D4; Spring Kafka надає `@RetryableTopic` (неблокуючі повтори через retry-топіки та DLT) — D6; екосистема Debezium дозволяє замінити polling-relay outbox на CDC без зміни контрактів подій.
- **Недоліки:** відсутні нативні відкладені повідомлення та per-message TTL — повтори реалізуються окремими retry-топіками; паралелізм споживання обмежений кількістю партицій, збільшення кількості партицій змінює розподіл ключів; найвищі вимоги до ресурсів серед альтернатив; модель «exactly-once» діє лише в межах Kafka, тому споживачі однаково повинні бути ідемпотентними.

### B. RabbitMQ 4.x (quorum queues, Streams)

Брокер черг з маршрутизацією через exchanges; quorum queues базуються на Raft.

- **Переваги:** гнучка маршрутизація (topic/headers exchanges); нативні DLX, TTL і priority; менше споживання ресурсів, ніж у Kafka, при порівнянному навантаженні; quorum queues забезпечують D4; RabbitMQ Streams надають журнал з повторним читанням.
- **Недоліки:** у моделі черг повідомлення видаляється після підтвердження, тому D5 досяжне лише через Streams, що означає дві моделі споживання в одному брокері; порядок у черзі зберігається лише при одному активному споживачі (single active consumer), горизонтальне масштабування зі збереженням порядку за ключем потребує плагіна consistent hash exchange та ручного керування кількістю черг; відкладені повтори з експоненційною затримкою потребують плагіна delayed message exchange або ланцюжка черг з TTL; аналог log compaction відсутній.

### C. Redis Streams (наявний Redis 7)

- **Переваги:** відсутній додатковий інфраструктурний компонент; consumer groups і повторне читання за ID; субмілісекундна латентність.
- **Недоліки:** дані зберігаються в оперативній пам'яті, тому 7 діб історії (D5) конкурують за пам'ять з кешем сесій і GEO-позиціями, що впливає на [SRS-NFR-PERF-05](../srs.md#srs-nfr-perf-05); довговічність залежить від налаштувань AOF (`appendfsync everysec` допускає втрату до 1 с даних), що не відповідає D4; механізм DLQ та повторів реалізується вручну через `XPENDING`/`XCLAIM`; Redis стає єдиною точкою відмови одночасно для кешу, rate limiting і подій.

### D. PostgreSQL Outbox без брокера (опитування таблиць outbox споживачами)

- **Переваги:** мінімальна інфраструктура; транзакційна узгодженість без проміжної ланки.
- **Недоліки:** кожен споживач опитує БД сервісу-власника, що порушує принцип database-per-service і створює зв'язність за схемою даних; навантаження опитування на primary PostgreSQL зростає пропорційно кількості споживачів; латентність визначається інтервалом опитування, тому D2 досягається лише при частому опитуванні з відповідним навантаженням на БД.

### Порівняльна матриця

| Критерій | Kafka | RabbitMQ | Redis Streams | PostgreSQL Outbox |
| --- | --- | --- | --- | --- |
| D3. Порядок за ключем при масштабуванні споживачів | Нативно (партиція) | Плагін + ручне шардування | В межах одного stream | В межах таблиці |
| D4. Довговічність при відмові вузла | RF 3, ISR 2 | Quorum queue (Raft) | Залежить від AOF | ACID PostgreSQL |
| D5. Повторне читання історії | Нативно (retention, compaction) | Лише Streams | Так, обмежено пам'яттю | Так, ціною зв'язності |
| D6. Повтори та DLQ | Retry-топіки + DLT (Spring Kafka) | DLX нативно, затримка — плагін | Вручну | Вручну |
| D7. Мінімальні ресурси (3 вузли) | ≈ 1,5 vCPU / 4,5 GiB | ≈ 1,5 vCPU / 3 GiB | 0 (наявний Redis) | 0 |
| Операційна складність | Висока | Середня | Низька | Низька |

## Decision (Рішення)

Обрано **Apache Kafka 3.8 у режимі KRaft** (3 брокери з об'єднаною роллю broker/controller) як єдиний брокер доменних подій.

Визначальні аргументи:

1. **Порядок за ключем без ручного шардування (D3).** Ключ партиціювання `requestId` гарантує послідовність подій Saga заявки, ключ `sessionId` — послідовність подій сесії присутності; масштабування споживачів до кількості партицій (6 на топік) не порушує порядок.
2. **Повторне читання як базова модель (D5).** Відновлення проєкції геозон в attendance-service після втрати даних виконується скиданням offset consumer group; топік `site.geofences` з log compaction зберігає актуальний стан кожного об'єкта. У RabbitMQ ця ж вимога потребує паралельного використання Streams і черг.
3. **Гарантії довговічності (D4)** конфігуруються декларативно: `replication.factor=3`, `min.insync.replicas=2`, `acks=all`, `enable.idempotence=true`.
4. **Неблокуючі повтори та DLQ (D6)** реалізуються стандартним механізмом `@RetryableTopic` (5 спроб, затримка 1–16 с, суфікс `-dlt`) без сторонніх плагінів брокера.

Конфігурація топіків: `<domain>.events` (6 партицій, retention 7 діб), `site.geofences` (compaction), `*-retry-N` та `*-dlt` (retention 14 діб).

## Consequences (Наслідки)

### Позитивні

- Сервіси не мають синхронних залежностей один від одного; відмова notification-service або ai-service не блокує check-in і заявки.
- Нові споживачі (аналітика, аудит) підключаються без змін у сервісах-виробниках.
- Debezium Outbox Event Router може замінити polling-relay без зміни формату подій.
- Kafka-заголовки переносять W3C `traceparent`, що забезпечує наскрізні траси ([SRS-NFR-OBS-03](../srs.md#srs-nfr-obs-03)).

### Негативні (Trade-offs)

- **Ресурси та FinOps.** Кластер Kafka займає ≈ 1,5 vCPU і 4,5 GiB RAM (3 × JVM heap 1 GiB + page cache) і 3 × 10 GiB PVC, тобто ≈ 28 % RAM-бюджету dev-кластера ([SRS-NFR-INFRA-02](../srs.md#srs-nfr-infra-02)). У хмарному середовищі керований Kafka-сервіс має найвищу вартість серед альтернатив; для дипломного проєкту прийнято self-hosted розгортання.
- **Операційна складність.** Необхідні Helm-чарт або оператор Strimzi, моніторинг consumer lag, under-replicated partitions і дискового простору; збільшення кількості партицій після запуску змінює розподіл ключів і потребує процедури міграції.
- **Відсутність нативної затримки повідомлень.** Retry-топіки збільшують кількість топіків утричі та ускладнюють контрактне тестування (кожен retry-топік — частина AsyncAPI-специфікації).
- **Ідемпотентність лишається на споживачі.** Outbox-relay забезпечує доставку «at-least-once», тому кожен споживач повинен вести таблицю оброблених `eventId` ([SRS-NFR-REL-05](../srs.md#srs-nfr-rel-05)).
- **CI/CD та тестування.** Інтеграційні тести потребують Testcontainers з Kafka (≈ 15–20 с старту на тестовий клас), що збільшує тривалість конвеєра ([SRS-NFR-INFRA-04](../srs.md#srs-nfr-infra-04)); застосовується спільний контейнер на модуль.
- **Еволюція схем.** Без Schema Registry сумісність контрактів подій забезпечується лише AsyncAPI-специфікацією та Pact message-тестами; несумісна зміна формату виявляється тільки на етапі CI.

### Ризики та заходи

| Ризик | Ймовірність | Захід |
| --- | --- | --- |
| Вичерпання RAM dev-кластера | Середня | `KAFKA_HEAP_OPTS=-Xmx1g`; для локальної розробки — 1 брокер з RF 1 (профіль `dev-lite`) |
| Неконтрольоване зростання consumer lag | Середня | Алерт `kafka_consumergroup_lag > 1000` протягом 5 хв |
| Отруєне повідомлення блокує партицію | Низька | Неблокуючі повтори та DLT, алерт на кожне повідомлення DLT |
| Vendor lock-in | Низька | Kafka — відкритий протокол з кількома сумісними реалізаціями; доменний код залежить від порту `DomainEventPublisher`, а не від Kafka API |

## Verification (Перевірка рішення)

- Chaos-тест: видалення одного брокера під навантаженням k6 не призводить до втрати подій ([SRS-NFR-REL-03](../srs.md#srs-nfr-rel-03)).
- Тест порядку: 1000 подій однієї заявки споживаються у порядку публікації при 3 репліках споживача.
- Тест перебудови проєкції: скидання offset `attendance-site-projection` відновлює геозони всіх об'єктів.
- Вимірювання p95 «outbox commit → push send» у Jaeger ([SRS-NFR-PERF-06](../srs.md#srs-nfr-perf-06)).

## Перегляд рішення

Рішення переглядається, якщо фактичне навантаження після апробації буде < 10 повідомлень/с і вимога D5 буде знята: у цьому разі RabbitMQ (quorum queues) забезпечить вимоги з меншими ресурсами.
